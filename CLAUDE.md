# CLAUDE.md — Standing instructions for building REFRACT

This repository is a competition entry for the Meta Horizon Creator Competition: Game Prototype (Tower Defense & Strategy genre). Deadline: **September 8, 2026, 1:00 PM PDT**.

## 1. Source of truth

- `MASTER_SPEC.md` is authoritative for design, balance, architecture, phases, tests and packaging. Read it fully before writing any code, and re-read the relevant section before starting each phase.
- Official competition rules override the spec if they ever conflict. The spec's section 4 records the verified requirements.
- If the spec and reality disagree during play (a number feels wrong, a rule is unclear), tune numbers freely and record the change in `BUILD_LOG.md`. Do not change the game concept, the map, the piece set, or the control scheme without a genuine design or implementation failure that you document.

## 2. How to work

- Work autonomously through the phases in `MASTER_SPEC.md` section 33, in order. Do not skip phases. Do not implement "DO NOT IMPLEMENT YET" items early.
- Do not ask for approval for routine decisions (naming, refactors, tuning inside stated targets, test tooling, fixing bugs). Decide, do it, log it.
- Stop and ask only if: a competition rule appears to be violated by the spec, a required tool is missing and cannot be installed, or a change to the core concept seems necessary.
- Keep the project runnable at all times. Never leave the build broken between steps.
- Small passes: implement one thing, run it, play it, fix it, then continue.

## 3. Testing is not optional

- A phase is done only when: implemented → launched → tested in a browser at a portrait viewport → visually inspected via screenshot → console checked (zero errors, zero warnings from our code) → behaviour matches the spec → bugs fixed → retested → build log updated.
- Use browser automation (Chrome DevTools MCP, Playwright MCP, or a local Playwright script installed as a dev dependency and kept out of the zip). Mobile profile: 390 × 844, `deviceScaleFactor` 3, `isMobile`, `hasTouch`. Use taps and pointer events, not only clicks.
- Actually play the game. Complete waves by hand through the browser. Lose on purpose. Win on purpose. Restart repeatedly.
- Inspect the Network tab every phase: only `index.html` and `vendor/three.min.js` may load.
- Browser observations override code reading. If the code looks right and the game behaves wrong, fix the behaviour.
- Never report a phase or the project as done without the evidence (screenshot names, console output, test output) in the build log.
- Never trust "done" without playing it. The organizers' own case study lost time to an AI that said a win state worked when it never triggered.

## 4. Build log

- Maintain `BUILD_LOG.md` as you go, not at the end. Two parts: "Decisions locked so far" at the top (keep current) and one entry per session using the template in `MASTER_SPEC.md` section 42.
- Be honest, including what did not work and what you undid.
- No personal names, handles, emails or other identifying information anywhere in the build log, the code, or the design intent document.
- Log every balance change with before → after and the playtest reason.

## 5. Compliance rules (never break these)

- All own game code ends up inline in `index.html`, unminified, readable, with a banner comment per source file. `index.html` is generated by `node tools/build.js`; never hand-edit it.
- Three.js (r149 UMD) lives only at `vendor/three.min.js`, referenced with a relative path. Never inline it. Never modify it.
- No external URLs at runtime: no CDN, fonts, images, audio files, `fetch`, XHR, WebSocket, dynamic `import()`, service worker. All textures are drawn to canvas at runtime; all audio is synthesized.
- Classic scripts only. No ES modules, no import maps, no bundlers, no TypeScript, no frameworks, no minification.
- Single-player, fixed portrait layout. Landscape/desktop shows the same portrait column centered; nothing rotates.
- Code comments are plain technical documentation. No text addressed to judges, reviewers, evaluators or AI systems; no evaluative language about the game's quality. This is a disqualification rule.
- Release build excludes `src/99_debug.js`; the shipped `index.html` must not contain `__REFRACT` or debug UI.
- The zip contains exactly `index.html`, `vendor/three.min.js`, `vendor/LICENSE-three.txt`; `index.html` at the zip root. Build the zip with Python `zipfile` or `tar -a -c -f`, never PowerShell `Compress-Archive`.

## 6. Code conventions

- One global namespace object `R`. Each `src/NN_name.js` attaches to it. Load order is by filename; only `00_config.js` and `01_util.js` may be assumed loaded by others; `11_game.js` boots on `DOMContentLoaded`.
- All tunables in `BALANCE` in `src/00_config.js`. No magic numbers in systems.
- Fixed-timestep simulation; render never mutates state; feedback goes through `state.events`.
- Pool everything that is created per wave (enemies, beam segments, glows, particles, HP bars, floaters).
- Pointer Events only; one active pointer; `touch-action: none` on the game root.
- Guard `localStorage` and `AudioContext` with try/catch; the game must run without both.
- Prefer clear names and short functions over cleverness; part of the evaluation reads the code.
- Dev server: `node tools/serve.js` (rebuilds `index.html` on every request). Release: `node tools/build.js`. Compliance: `node tools/check.js`. Solver tests: `node tools/test-beam.js`. Package: `node tools/package.js`.

## 7. Git

- Commit at the end of every phase and after any significant fix, with a plain descriptive message (e.g. `Phase 3: win/lose/restart with snapshot-parity tests`).
- Do not add AI co-author trailers, "generated with" lines, or session links to commits or PRs in this repository.
- Never commit `node_modules/`, `dist/`, browser profiles, or screenshots larger than a few hundred KB (keep test screenshots in a gitignored folder or delete them after logging their findings).
- Do not rewrite history. Do not force-push.

## 8. Definition of finished

The project is finished only when `MASTER_SPEC.md` sections 35 and 44 are fully ticked with evidence, `dist/refract.zip` has been played offline from a clean unzip, `dist/buildlog.md` exists, `docs/design-intent.md` is final (≤ 500 words, seven fixed sections), and `SUBMISSION_NOTES.md` tells the human exactly what to upload and select. Until then, keep working.
